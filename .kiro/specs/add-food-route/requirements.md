# Requirements Document

## Introduction

This feature adds a route to Foodstarter where users add a food entry, see every saved entry, and delete an entry on the same page. The page uses a gradient visual style. Entries are stored in the `foods` table (existing columns: name, meal type, calories, notes, eaten at). This feature adds four optional columns to the `foods` table: `protein_g`, `carbs_g`, `fat_g` and `serving_size`. Edit is out of scope.

### Assumptions

- The four new columns are nullable and optional. Existing rows receive NULL for each new column and continue to display correctly.
- `protein_g`, `carbs_g` and `fat_g` are integer grams from 0 to 10000 inclusive.
- `serving_size` is free text of at most 100 characters (`varchar(100)`), such as "1 cup" or "150 g".
- The schema change is delivered as a Drizzle migration created with `drizzle-kit generate` and applied with `drizzle-kit migrate`. `drizzle-kit push` is not used.

## Glossary

- **Foodstarter**: The food tracking web application.
- **Add_Food_Page**: The route at `/foods` that contains the Food_Form and the Food_List.
- **Food_Form**: The form on the Add_Food_Page used to enter a new Food_Entry.
- **Food_List**: The section of the Add_Food_Page that displays all saved Food_Entries.
- **Food_Entry**: One saved row of the `foods` table.
- **Meal_Type**: One of `breakfast`, `lunch`, `dinner`, `snack`.
- **Create_Food_Function**: The POST server function in `src/server/` that validates input and inserts a Food_Entry.
- **List_Foods_Function**: The GET server function in `src/server/` that returns all Food_Entries.
- **Validator**: The Zod schema that checks Food_Form input at the server function boundary.
- **Delete_Food_Function**: The POST server function in `src/server/` that validates a Food_Entry identifier and deletes the matching Food_Entry.
- **Delete_Control**: The button on each Food_Entry card in the Food_List that starts deletion of that Food_Entry.
- **Delete_Confirmation**: The step shown after the user activates a Delete_Control, in which the user either confirms or cancels the deletion of that Food_Entry.
- **Entry_Id**: The `id` column of a Food_Entry, a UUID.
- **Food_Total**: The total number of Food_Entries displayed by the Food_List.
- **Macro_Fields**: The three optional macro nutrient fields of a Food_Entry: protein, carbs and fat, stored in the `protein_g`, `carbs_g` and `fat_g` columns as integer grams.
- **Serving_Size**: The optional free-text description of the amount eaten (for example "1 cup" or "150 g"), stored in the `serving_size` column.
- **Food_Migration**: The Drizzle migration generated by `drizzle-kit generate` that adds the Macro_Fields and Serving_Size columns to the `foods` table.
- **Absent_Value**: A Macro_Fields or Serving_Size value that is NULL in the `foods` table.

## Requirements

### Requirement 1: Add Food Page Route

**User Story:** As a user, I want a dedicated page for adding food, so that I can reach the add-food form directly.

#### Acceptance Criteria

1. WHEN a user navigates to the path `/foods`, THE Foodstarter SHALL render the Add_Food_Page without a navigation error.
2. WHEN the Add_Food_Page finishes loading, THE Add_Food_Page SHALL display exactly one Food_Form and exactly one Food_List on the same page without requiring navigation to another path.
3. WHEN the Add_Food_Page finishes loading, THE Add_Food_Page SHALL display exactly one top-level heading above the Food_Form, with non-empty text that contains the words "Add Food".
4. IF the Food_List data fails to load, THEN THE Add_Food_Page SHALL still display the heading and the Food_Form, and SHALL display an error indication in place of the Food_List stating that the list could not be loaded.

### Requirement 2: Food Entry Input Fields

**User Story:** As a user, I want to enter the details of a food I ate, so that the entry records what, when and how much I ate.

#### Acceptance Criteria

1. THE Food_Form SHALL provide input fields for name, Meal_Type, calories, eaten-at date and time, notes, protein, carbs, fat and Serving_Size.
2. THE Food_Form SHALL provide exactly four Meal_Type options (breakfast, lunch, dinner, snack) as the only selectable values, and SHALL NOT allow free-text entry for Meal_Type.
3. WHEN the Food_Form loads, THE Food_Form SHALL set the eaten-at field to the user's current local date and time, accurate to the minute.
4. THE Food_Form SHALL mark name, Meal_Type, calories and eaten-at as required fields.
5. THE Food_Form SHALL leave the notes field optional.
6. THE Food_Form SHALL limit name to 1 to 255 characters after trimming leading and trailing whitespace.
7. THE Food_Form SHALL accept calories only as a whole number from 0 to 100,000.
8. THE Food_Form SHALL limit notes to a maximum of 1,000 characters.
9. THE Food_Form SHALL leave each of the Macro_Fields and the Serving_Size field optional and empty by default.
10. THE Food_Form SHALL accept each of the Macro_Fields only as a whole number from 0 to 10,000.
11. THE Food_Form SHALL limit Serving_Size to a maximum of 100 characters after trimming leading and trailing whitespace.
12. IF a Macro_Fields value is not a whole number from 0 to 10,000 when the user submits, THEN THE Food_Form SHALL display the error message "Enter a whole number from 0 to 10,000" next to that field.
13. IF the Serving_Size value exceeds 100 characters after trimming when the user submits, THEN THE Food_Form SHALL display the error message "Serving size must be 100 characters or fewer" next to the Serving_Size field.
14. IF a required field is empty or any field value is outside its allowed bounds when the user submits, THEN THE Food_Form SHALL block submission, display an error message next to each invalid field indicating the violated rule, and retain all values the user entered.

### Requirement 3: Input Validation

**User Story:** As a user, I want my input checked, so that only valid food entries are saved.

#### Acceptance Criteria

1. THE Validator SHALL require name to be a string of 1 to 255 characters after leading and trailing whitespace is removed.
2. THE Validator SHALL require calories to be a whole number from 0 to 100000 inclusive, and SHALL reject decimal values, negative values, non-numeric values and empty values.
3. THE Validator SHALL require Meal_Type to be exactly one of `breakfast`, `lunch`, `dinner` or `snack` (case-sensitive), and SHALL reject any other value including an empty value.
4. THE Validator SHALL accept notes as an optional string of 0 to 1000 characters, and SHALL treat an omitted or empty notes value as valid.
5. THE Validator SHALL accept eaten-at as an optional value that parses to a valid calendar date and time, and SHALL treat an omitted or empty eaten-at value as valid.
6. THE Validator SHALL accept each of the Macro_Fields as an optional whole number from 0 to 10000 inclusive, and SHALL reject decimal values, negative values, values above 10000 and non-numeric values.
7. WHEN a Macro_Fields input is omitted or empty, THE Validator SHALL treat the value as valid and THE Create_Food_Function SHALL store NULL for that column, not 0.
8. THE Validator SHALL accept Serving_Size as an optional string of at most 100 characters after leading and trailing whitespace is removed, and SHALL reject a longer string.
9. WHEN a Serving_Size input is omitted, empty or contains only whitespace, THE Create_Food_Function SHALL store NULL for the `serving_size` column.
10. WHEN a Macro_Fields input is the number 0, THE Validator SHALL accept the value and THE Create_Food_Function SHALL store 0.
11. IF the Food_Form input fails validation, THEN THE Add_Food_Page SHALL display an error message next to each invalid field, SHALL retain the values the user entered in all fields, and SHALL NOT create a Food_Entry.
12. WHEN a request reaches the Create_Food_Function, THE Create_Food_Function SHALL apply the Validator before any database write.
13. IF a request reaching the Create_Food_Function fails validation, THEN THE Create_Food_Function SHALL return an error identifying each invalid field and SHALL NOT write to the database.

### Requirement 4: Save Food Entry

**User Story:** As a user, I want to save a food entry, so that I can keep a record of what I ate.

#### Acceptance Criteria

1. WHEN the user submits a valid Food_Form, THE Create_Food_Function SHALL insert exactly one Food_Entry into the `foods` table using the submitted values.
2. WHEN the user submits a valid Food_Form without an eaten-at value, THE Create_Food_Function SHALL store the current server time as eaten-at.
3. WHEN the Create_Food_Function inserts a Food_Entry successfully, THE Create_Food_Function SHALL return the saved Food_Entry, including its generated identifier, stored eaten-at value, stored Macro_Fields values and stored Serving_Size value.
4. WHEN the user submits a valid Food_Form with Macro_Fields or Serving_Size values, THE Create_Food_Function SHALL store each submitted value in the matching column of the inserted Food_Entry, with the Serving_Size stored after leading and trailing whitespace is removed.
5. WHEN the user submits a valid Food_Form with a Macro_Fields or Serving_Size field left empty, THE Create_Food_Function SHALL store NULL in the matching column and SHALL return NULL for that value.
6. WHEN the Create_Food_Function returns a saved Food_Entry, THE Add_Food_Page SHALL show the new Food_Entry in the Food_List within 2 seconds, without a manual page reload.
7. WHEN the Create_Food_Function returns a saved Food_Entry, THE Food_Form SHALL reset every field to its initial value.
8. WHILE a Food_Form submission is in progress, THE Food_Form SHALL disable the submit button, so that one submission cannot create more than one Food_Entry.
9. IF the database write fails, THEN THE Create_Food_Function SHALL insert no Food_Entry, log the error details on the server only, and return a generic failure message that contains no database or stack details.
10. IF the Create_Food_Function returns a failure, THEN THE Add_Food_Page SHALL display the failure message, keep every entered value in the Food_Form, leave the Food_List unchanged, and re-enable the submit button.
11. IF the Create_Food_Function receives input that fails validation, THEN THE Create_Food_Function SHALL insert no Food_Entry and return an error message identifying each invalid field.

### Requirement 5: List All Food Entries

**User Story:** As a user, I want to see all my saved foods, so that I can review what I have eaten.

#### Acceptance Criteria

1. WHEN the Add_Food_Page loads, THE List_Foods_Function SHALL return every Food_Entry in the `foods` table without pagination or truncation, and THE Food_List SHALL render the returned Food_Entries within 2 seconds for a table of up to 1,000 rows.
2. THE List_Foods_Function SHALL order Food_Entries by eaten-at descending, then by created-at descending, so that the Food_Entry with the latest eaten-at appears first and Food_Entries with equal eaten-at values appear with the most recently created first.
3. THE Food_List SHALL display name, Meal_Type, calories (as a whole number followed by the unit "kcal"), eaten-at (as date and time in the user's local time zone) and notes for each Food_Entry.
4. WHERE a Food_Entry has notes that are null, empty or contain only whitespace, THE Food_List SHALL omit the notes line for that Food_Entry.
5. WHERE a Food_Entry has a non-NULL protein, carbs or fat value, THE Food_List SHALL display that value for the Food_Entry as a whole number of grams followed by the unit "g", labeled "Protein", "Carbs" or "Fat" respectively, including a value of 0.
6. WHERE a Food_Entry has a non-NULL Serving_Size, THE Food_List SHALL display the Serving_Size text for that Food_Entry.
7. WHERE a Food_Entry has an Absent_Value for protein, carbs, fat or Serving_Size, THE Food_List SHALL omit the label and value for that field on that Food_Entry card, and SHALL NOT display a placeholder such as "0", "-" or "N/A" in its place.
8. WHEN the List_Foods_Function returns a Food_Entry created before the Food_Migration, THE Food_List SHALL display that Food_Entry with its name, Meal_Type, calories, eaten-at and notes, and with no protein, carbs, fat or Serving_Size content.
9. WHEN the `foods` table contains no rows, THE Food_List SHALL display an empty-state message that invites the user to add the first food, and THE Food_List SHALL display a total of 0 Food_Entries.
10. WHEN the List_Foods_Function returns one or more Food_Entries, THE Food_List SHALL display the total number of Food_Entries, and that number SHALL equal the count of Food_Entries rendered in the list.
11. IF the List_Foods_Function fails, THEN THE Add_Food_Page SHALL display an error message indicating that the foods could not be loaded through the route error component, SHALL NOT render a partial Food_List, and THE List_Foods_Function SHALL log the error details on the server only, without including them in the message shown to the user.

### Requirement 6: Visual Design

**User Story:** As a user, I want an attractive page, so that tracking food feels pleasant.

#### Acceptance Criteria

1. THE Add_Food_Page SHALL render a background that transitions between at least two distinct colors, built with Tailwind CSS gradient utilities, and the background SHALL cover the full viewport height.
2. THE Food_Form SHALL render inside a card with a corner radius of at least 8px and a visible box shadow, on a background that differs from the page background.
3. THE Food_List SHALL render each Food_Entry as a separate card with a corner radius of at least 8px.
4. THE Add_Food_Page SHALL display each Meal_Type value (every value defined in the Glossary) with a badge whose background color differs from that of every other Meal_Type badge.
5. THE Add_Food_Page SHALL render body text, badge text and form label text at a contrast ratio of at least 4.5:1 against the background directly behind that text.
6. WHILE the viewport width is below 768px, THE Add_Food_Page SHALL lay out the Food_Form and the Food_List in a single column, with the Food_Form displayed before the Food_List.
7. WHILE the viewport width is 768px or above, THE Add_Food_Page SHALL lay out the Food_Form and the Food_List side by side in two columns.
8. WHILE the viewport width is between 320px and 1920px, THE Add_Food_Page SHALL render all content without horizontal scrolling, including when a Food_Entry name contains 100 characters with no spaces, which SHALL wrap or truncate within its card.

### Requirement 7: Project Architecture

**User Story:** As a developer, I want the feature to follow the project architecture, so that the code stays consistent and maintainable.

#### Acceptance Criteria

1. WHEN the Add_Food_Page route is loaded, THE Add_Food_Page SHALL fetch Food_Entries through a route loader that calls the List_Foods_Function, and THE Add_Food_Page SHALL NOT query the database directly from the route or its components.
2. WHEN a user submits the Food_Form, THE Food_Form SHALL invoke the Create_Food_Function through `useServerFn`, and THE Food_Form SHALL NOT query the database directly.
3. THE Create_Food_Function SHALL use the POST method, THE Delete_Food_Function SHALL use the POST method, and THE List_Foods_Function SHALL use the GET method.
4. THE Foodstarter SHALL place every server function that accesses the database in a file under `src/server/`, and SHALL import the Drizzle schema from `src/db/schema.ts`.
5. THE Foodstarter SHALL define the Food_Entry TypeScript type using the Drizzle `$inferSelect` type and the new-entry input type using `$inferInsert`, with no hand-written duplicate type definitions of the same fields, including the Macro_Fields and Serving_Size fields, whose types SHALL be nullable as derived from the schema columns.
6. THE Foodstarter SHALL obtain the list of allowed Meal_Type values only from the `mealTypes` constant in `src/db/schema.ts`, with no duplicate literal list of Meal_Type values elsewhere in the feature code.
7. IF the List_Foods_Function, Create_Food_Function or Delete_Food_Function fails, THEN THE Foodstarter SHALL return or throw an error that the calling route or form can display, SHALL record error details on the server only, and SHALL NOT expose database error details to the client.
8. WHEN `pnpm check` is run after the feature is added, THE Foodstarter SHALL complete the Biome check with zero errors and zero warnings.
9. WHEN a user confirms a Delete_Confirmation, THE Food_List SHALL invoke the Delete_Food_Function through `useServerFn`, and THE Food_List SHALL NOT query the database directly.
10. THE Foodstarter SHALL define the `protein_g`, `carbs_g`, `fat_g` and `serving_size` columns in `src/db/schema.ts` as nullable columns of the `foods` table, with `protein_g`, `carbs_g` and `fat_g` as integer columns and `serving_size` as `varchar(100)`.
11. THE Foodstarter SHALL generate the Food_Migration with `drizzle-kit generate` and apply the Food_Migration with `drizzle-kit migrate`, and SHALL NOT use `drizzle-kit push` to apply the schema change.
12. WHEN the Food_Migration is applied to a `foods` table that contains existing rows, THE Foodstarter SHALL keep every existing row and set protein, carbs, fat and Serving_Size to NULL for each existing row.

### Requirement 8: Delete Food Entry

**User Story:** As a user, I want to delete a food entry, so that I can remove entries I added by mistake or no longer want to keep.

#### Acceptance Criteria

1. THE Food_List SHALL display exactly one Delete_Control on each Food_Entry card.
2. WHEN the user activates a Delete_Control, THE Food_List SHALL display a Delete_Confirmation that identifies the Food_Entry by name and offers a confirm action and a cancel action, and THE Food_List SHALL NOT invoke the Delete_Food_Function before the user confirms.
3. WHEN the user cancels a Delete_Confirmation, THE Food_List SHALL close the Delete_Confirmation, keep the Food_Entry in the Food_List, and make no call to the Delete_Food_Function.
4. WHEN a request reaches the Delete_Food_Function, THE Delete_Food_Function SHALL validate that the Entry_Id is a string in UUID format with a Zod schema before any database write.
5. IF a request reaching the Delete_Food_Function contains an Entry_Id that fails validation, THEN THE Delete_Food_Function SHALL return an error stating that the identifier is invalid and SHALL NOT write to the database.
6. WHEN the Delete_Food_Function receives a valid Entry_Id that matches a row in the `foods` table, THE Delete_Food_Function SHALL delete exactly that one row and SHALL leave every other row in the `foods` table unchanged.
7. WHEN the Delete_Food_Function deletes a Food_Entry successfully, THE Delete_Food_Function SHALL return the Entry_Id of the deleted Food_Entry.
8. WHEN the Delete_Food_Function returns a successful result, THE Food_List SHALL remove the deleted Food_Entry card within 2 seconds, without a manual page reload.
9. WHEN the Food_List removes a deleted Food_Entry, THE Food_List SHALL update the Food_Total so that the Food_Total equals the count of Food_Entries rendered in the list.
10. WHEN the Food_List removes the last remaining Food_Entry, THE Food_List SHALL display the empty-state message and a Food_Total of 0.
11. IF the Delete_Food_Function receives a valid Entry_Id that matches no row in the `foods` table, THEN THE Delete_Food_Function SHALL return a not-found error stating that the Food_Entry does not exist, and SHALL leave every row in the `foods` table unchanged.
12. IF the Delete_Food_Function returns a not-found error, THEN THE Food_List SHALL display the not-found message and remove the matching Food_Entry card from the Food_List.
13. IF the database delete fails, THEN THE Delete_Food_Function SHALL log the error details on the server only and return a generic failure message that contains no database or stack details.
14. IF the Delete_Food_Function returns a failure other than not-found, THEN THE Food_List SHALL display the failure message, keep the Food_Entry in the Food_List, keep the Food_Total unchanged, and re-enable the Delete_Control for that Food_Entry.
15. WHILE a deletion of a Food_Entry is in progress, THE Food_List SHALL disable the Delete_Control and the confirm action of the Delete_Confirmation for that Food_Entry, so that one confirmation cannot send more than one delete request.
16. WHEN the same Entry_Id is submitted to the Delete_Food_Function twice in succession, THE Delete_Food_Function SHALL delete the row on the first request and return a not-found error on the second request, and the `foods` table SHALL be identical after the second request and after the first request (idempotent end state).
17. THE Delete_Control SHALL have an accessible name that includes the name of its Food_Entry.
